# UWB Q1 문제 해결 가이드

**GrowSpace UWB 크리에이터 키트 Q1**(개발자 태그·리스너·게이트웨이) 배선이나 데이터 수신에서
자주 겪는 문제와 해결법이다. 여기 없는 문제는
[이슈를 등록](https://github.com/FreeGrow/growspace-uwb-q1-examples/issues)하거나
[전체 문서](https://grow-space.io/docs/q1/)를 확인한다.

English version: [troubleshooting.md](troubleshooting.md)

## 시리얼 포트에 데이터가 안 나온다

**증상:** `serial_reader.py`는 연결되는데 아무 줄도 출력되지 않거나 타임아웃난다.

1. **`lep` 명령을 먼저 보낸다.** 태그와 리스너는 `lep` 명령을 받기 전까지 조용하다. 이 명령 없이는
   아무것도 스트리밍되지 않는다.
2. **보드레이트를 확인한다.** 키트 통신 속도는 **115200bps**다. 보드레이트가 다르면 "데이터 없음"
   이나 깨진 텍스트로 보일 뿐 에러가 뜨지 않는다.
3. **TX↔RX를 교차 연결한다.** TX→TX, RX→RX로 잘못 연결하면 포트는 정상적으로 열리지만
   아무것도 수신되지 않는다. 두 선을 바꿔 연결한다.
4. **포트 이름을 확인한다.** 리눅스는 보통 `/dev/ttyUSB0`나 `/dev/ttyACM0`, 윈도우는 `COMx` 포트다.
   `python -m serial.tools.list_ports`로 연결된 포트 목록을 확인할 수 있다.

## 텍스트가 깨지거나 일부만 나온다

**증상:** `POS,-3.4`처럼 잘린 값이 보이거나 알아볼 수 없는 문자가 섞여 나온다.

- 거의 항상 **보드레이트 불일치**다. 양쪽 다 115200으로 맞췄는지 다시 확인한다.
- 브레드보드의 헐겁거나 너무 긴 점퍼선도 이 속도에서 UART 신호를 깨뜨릴 수 있다. 배선은 짧게,
  접촉은 확실하게 한다.

## 위치가 안정되지 않는다 / `qf`가 계속 낮다

**증상:** 좌표는 들어오는데 품질 지수(`qf`)가 계속 40~50 미만이거나 위치가 튄다.

- **`qf`는 0~100 신뢰도 점수다.** 60 이상이면 대체로 안정적으로 쓸 수 있고, 그 미만은 노이즈로
  보고 필터링하는 게 좋다(`python/serial_reader.py`의 `--min-qf` 예시 참고).
- **가시선(line-of-sight)이 중요하다.** 두꺼운 벽이나 금속 선반을 지나거나, 태그가 리스너 설치면에
  너무 가까우면 UWB 측위 정확도가 떨어진다.
- **리스너 배치 형태.** 리스너들이 거의 일직선으로 있으면 그 축에 수직인 방향의 정확도가 떨어진다.
  가능하면 2차원으로 넓게 분산 배치한다.

## 라즈베리파이: UART가 응답이 없거나 파이가 리셋된다

**증상:** `/dev/serial0`에 아무것도 안 뜨거나, 태그를 연결하자마자 라즈베리파이가 불안정해진다.

- **태그는 항상 3.3V 쪽만 쓰고, 5V 쪽은 쓰지 않는다.** 개발자 태그에는 커넥터가 두 개 있다 —
  **오른쪽이 5V, 왼쪽이 3.3V**다. 5V 쪽을 라즈베리파이 GPIO UART 핀에 연결하면 파이의 UART
  입력이 손상될 수 있다. 파이의 GPIO는 3.3V 로직 레벨이기 때문이다.
- 먼저 **리눅스 시리얼 콘솔을 비활성화**한다(`raspi-config` → Interface Options → Serial Port →
  로그인 셸: No, 하드웨어 활성화: Yes). 안 하면 OS가 포트를 두고 스크립트와 충돌한다.
- 전체 가이드: https://grow-space.io/docs/q1/raspberry-pi/

## ESP32: 시리얼 연결이 자꾸 끊기거나 리셋된다

**증상:** 태그 데이터를 읽는 도중 USB-시리얼 연결이 간헐적으로 끊기거나 보드가 재부팅된다.

- 가능하면 소프트웨어 시리얼 대신 **하드웨어 UART**(예: `Serial1`/`Serial2`)를 쓴다. ESP32는
  하드웨어 UART가 여러 개라 115200bps에서 소프트웨어 시리얼보다 훨씬 안정적이다.
- 일부 ESP32 보드는 태그가 같은 USB 전원 라인에서 전류를 끌어가면 부하로 브라운아웃이 난다.
  랜덤 리셋이 보이면 유전원 허브나 별도 5V 전원을 쓴다.
- 전체 가이드: https://grow-space.io/docs/q1/esp32/

## 아두이노 우노: AltSoftSerial이 아무것도 수신하지 못한다

**증상:** `arduino/uno_altsoftserial`이 컴파일·업로드는 되는데 아무것도 출력되지 않는다.

- **AltSoftSerial은 우노에서 특정 핀에 고정**돼 있다(이 예제에서는 RX가 D8, TX가 D9). 라이브러리를
  바꾸지 않는 한 임의의 핀으로 옮길 수 없다.
- 우노의 하나뿐인 하드웨어 `Serial`은 보통 USB 디버그 출력용이라, 이 예제는 태그 연결에
  AltSoftSerial을 쓴다 — 태그를 D0/D1에 연결하지 않는다.
- 여러 시리얼을 동시에 읽어야 한다면 여유 하드웨어 `Serial1`/`Serial2`/`Serial3`가 있는
  **아두이노 메가 2560**(`arduino/mega_serial1` 참고)이 소프트웨어 시리얼보다 안정적이다.

## MQTT: 게이트웨이 메시지가 안 온다

**증상:** `mqtt_subscriber.py`는 브로커에 연결되는데 `uwb/gateway/...` 토픽에 아무 메시지도
안 뜬다.

- 게이트웨이와 구독 스크립트가 **같은 MQTT 브로커·토픽 프리픽스**를 보고 있는지 확인한다 —
  구독 스크립트뿐 아니라 게이트웨이 자체에 설정된 브로커 주소도 확인한다.
- 게이트웨이 페이로드는 `tags` 배열을 가진 JSON이다(`{"gatewayID":"...","tags":[{"id":"...",
  "x":...,"y":...,"z":...}]}`). 토픽을 필터링한다면 와일드카드가 게이트웨이 ID 구간까지
  포함하는지 확인한다.
- 방화벽이 있는 네트워크는 서브넷 간 MQTT 포트(1883, TLS는 8883)를 막는 경우가 있다.
  게이트웨이와 구독 머신이 실제로 브로커에 도달하는지 확인한다.
